# Terragrunt Structure and Naming

## Source

- Terragrunt Quick Start: https://terragrunt.gruntwork.io/docs/getting-started/quick-start/
- Infrastructure Live Example: https://github.com/gruntwork-io/terragrunt-infrastructure-live-example

## Core Philosophy

**Terragrunt naming is directory-based, not string-based.**

Unlike other systems that encode metadata in resource names or tags, Terragrunt uses:
- **Directory hierarchy** to organize environments, regions, and components
- **File naming conventions** for configuration files
- **Module references** for reusable infrastructure patterns

## Hard Requirements (MUST)

### terragrunt.hcl File

- Every Terragrunt "unit" (deployable component) requires a `terragrunt.hcl` file
- File must be at root of unit directory
- Contains configuration for that specific unit instance

### Directory Structure Rules

- Use forward slashes for paths (even on Windows)
- No spaces in directory names
- Lowercase recommended for consistency
- Hyphens preferred for multi-word names

## Recommended Structure

### Infrastructure Live Repository Pattern

The canonical Terragrunt pattern from Gruntwork:

```
infrastructure-live/
├── _global/                           # Non-regional resources
│   ├── route53/
│   │   └── terragrunt.hcl
│   └── iam/
│       └── terragrunt.hcl
├── prod/
│   ├── us-east-1/
│   │   ├── vpc/
│   │   │   └── terragrunt.hcl
│   │   ├── services/
│   │   │   ├── frontend-app/
│   │   │   │   └── terragrunt.hcl
│   │   │   └── backend-app/
│   │   │       └── terragrunt.hcl
│   │   └── data-storage/
│   │       ├── mysql/
│   │       │   └── terragrunt.hcl
│   │       └── redis/
│   │           └── terragrunt.hcl
│   └── us-west-2/
│       └── (same structure)
├── staging/
│   └── us-east-1/
│       └── (same structure)
└── dev/
    └── us-east-1/
        └── (same structure)
```

### Directory Hierarchy Layers

**Layer 1 — Environment:**
```
<environment>/
```

Examples: `prod/`, `staging/`, `dev/`, `qa/`, `sandbox/`

**Layer 2 — Region:**
```
<environment>/<region>/
```

Examples: `prod/us-east-1/`, `staging/eu-west-1/`

**Layer 3 — Component Category (Optional):**
```
<environment>/<region>/<category>/
```

Examples: `services/`, `data-storage/`, `networking/`, `security/`

**Layer 4 — Component:**
```
<environment>/<region>/<category>/<component>/
```

Examples: `frontend-app/`, `mysql/`, `vpc/`, `bastion/`

## File Naming Conventions

### terragrunt.hcl

- Primary configuration file for each unit
- Defines:
  - Module source (`terraform.source`)
  - Input variables (`inputs`)
  - Dependencies (`dependency`, `dependencies`)
  - Remote state configuration
  - Hooks and other Terragrunt features

**Example:**
```hcl
terraform {
  source = "git::https://github.com/org/modules.git//vpc?ref=v1.0.0"
}

inputs = {
  vpc_name = "prod-vpc"
  cidr_block = "10.0.0.0/16"
}
```

### terragrunt.hcl in Root (Optional)

- Place `terragrunt.hcl` at repo root for shared configuration
- Inherited by all child units via `include` blocks
- Contains:
  - Remote state configuration
  - Provider configuration
  - Common variables
  - Retry configuration

### .terragrunt-cache/

- Generated by Terragrunt
- Contains downloaded modules and Terraform working directory
- Add to `.gitignore`
- Safe to delete anytime

## Common Patterns

### DRY Configuration with Includes

**Root terragrunt.hcl:**
```hcl
# terragrunt.hcl (root)
remote_state {
  backend = "s3"
  config = {
    bucket = "my-terraform-state"
    key    = "${path_relative_to_include()}/terraform.tfstate"
    region = "us-east-1"
  }
}
```

**Child unit:**
```hcl
# prod/us-east-1/vpc/terragrunt.hcl
include "root" {
  path = find_in_parent_folders()
}

terraform {
  source = "git::https://github.com/org/modules.git//vpc"
}

inputs = {
  vpc_name = "prod-vpc"
}
```

### Unit Naming

Units are identified by their directory path:

```
prod/us-east-1/services/frontend-app
```

**Components:**
- Environment: `prod`
- Region: `us-east-1`
- Category: `services`
- Unit: `frontend-app`

### Stack Operations

**Running all units in a stack:**
```bash
terragrunt run --all apply
```

**From specific directory:**
```bash
cd prod/us-east-1
terragrunt run --all apply
```

Terragrunt automatically:
- Discovers all units in subdirectories
- Builds dependency graph
- Runs in correct order

### Dependency Naming

Dependencies reference other units by path:

```hcl
# backend-app/terragrunt.hcl
dependency "vpc" {
  config_path = "../../../networking/vpc"
}

dependency "rds" {
  config_path = "../../data-storage/mysql"
}

inputs = {
  vpc_id = dependency.vpc.outputs.vpc_id
  db_host = dependency.rds.outputs.endpoint
}
```

## Directory Naming Patterns

### Environment Names

**Standard:**
- `prod` — Production
- `staging` — Staging/Pre-production
- `dev` — Development
- `qa` — QA/Testing
- `sandbox` — Experimental

**Multi-prod:**
- `prod-primary`
- `prod-dr` — Disaster recovery
- `prod-blue`, `prod-green` — Blue/green deployment

### Region Names

Use AWS region identifiers:
- `us-east-1`, `us-west-2`, `eu-west-1`
- Or: `use1`, `usw2`, `euw1` (abbreviated)

### Component Category Names

**Common categories:**
- `networking` — VPCs, subnets, routing
- `services` — Application services
- `data-storage` — Databases, caches, object storage
- `security` — Security groups, WAF, KMS
- `compute` — EC2, ECS, Lambda
- `monitoring` — CloudWatch, alerting

### Component Names

**Pattern:**
```
<service-type>-<role>
```

**Examples:**
- `frontend-app`
- `backend-api`
- `worker-queue`
- `mysql-primary`
- `redis-cache`
- `vpc-main`
- `bastion-host`

## Configuration Layers

### Global Configuration

Place non-regional resources in `_global/` or `global/`:

```
_global/
├── iam/
│   └── terragrunt.hcl
├── route53/
│   └── terragrunt.hcl
└── cloudfront/
    └── terragrunt.hcl
```

### Regional Configuration

Place regional resources under `<environment>/<region>/`:

```
prod/us-east-1/
├── vpc/
├── ec2/
└── rds/
```

### Account-Level Configuration

For multi-account setups:

```
accounts/
├── prod/
│   ├── account.hcl
│   └── us-east-1/
│       └── (resources)
├── staging/
│   ├── account.hcl
│   └── us-east-1/
│       └── (resources)
```

## Module Source References

### Git References

```hcl
terraform {
  source = "git::https://github.com/org/modules.git//vpc?ref=v1.0.0"
}
```

### Local Modules

```hcl
terraform {
  source = "../../../modules/vpc"
}
```

### Terraform Registry

```hcl
terraform {
  source = "terraform-aws-modules/vpc/aws//."
}
```

## Input Variable Patterns

### Environment-Specific Inputs

Use `terragrunt.hcl` for environment-specific values:

```hcl
inputs = {
  instance_count = 3              # prod-specific
  instance_type = "t3.large"      # prod-specific
  environment = "prod"
  region = "us-east-1"
}
```

### Shared Inputs

Use root `terragrunt.hcl` for shared values:

```hcl
# Root terragrunt.hcl
inputs = {
  aws_region = "us-east-1"
  common_tags = {
    ManagedBy = "Terragrunt"
    Repository = "infrastructure-live"
  }
}
```

## DAG (Dependency Graph)

Terragrunt builds a directed acyclic graph from dependencies:

```hcl
# Example dependency chain:
# vpc → subnets → security-groups → rds → app
```

**Running the stack:**
- Terragrunt determines execution order automatically
- Runs independent units in parallel
- Waits for dependencies before dependent units

## Mock Outputs

For planning before dependencies are applied:

```hcl
dependency "vpc" {
  config_path = "../vpc"
  
  mock_outputs = {
    vpc_id = "vpc-mock-12345"
    subnet_ids = ["subnet-mock-1", "subnet-mock-2"]
  }
  
  mock_outputs_allowed_terraform_commands = ["plan"]
}
```

## Constraints

| Element | Constraint |
|---|---|
| Directory names | No spaces, lowercase recommended |
| File name | Must be `terragrunt.hcl` |
| Cache directory | `.terragrunt-cache` (auto-generated) |
| Path depth | No hard limit, but practical limit ~5-6 levels |

## Rationale

### Why Directory-Based

- Natural hierarchy
- Easy to visualize structure
- Simple to navigate
- Works with file system tools
- No encoding of metadata in strings

### Why Flat Unit Directories

- Each unit is independent
- Clear what gets deployed together
- Easy to diff and version control
- Matches Terraform's unit-of-work model

### Why Relative Paths for Dependencies

- Works when repository is cloned
- Portable across environments
- No hardcoded paths

## Anti-Patterns to Avoid

- ❌ Deeply nested directory structures (>6 levels)
- ❌ Encoding too much metadata in directory names: `prod-us-east-1-vpc-blue-v2`
- ❌ Inconsistent naming across environments (e.g., `prod/` vs `production/`)
- ❌ Mixing component types in same directory
- ❌ Not using categories for large numbers of components
- ❌ Absolute paths in dependencies
- ❌ Spaces in directory names
- ❌ Very long directory names

## Integration with Other Tools

### Terraform Modules

Terragrunt units reference reusable Terraform modules:

```
infrastructure-live/        # Terragrunt (instances)
infrastructure-modules/     # Terraform (patterns)
```

### CI/CD

Directory structure enables targeted deployments:

```bash
# Deploy only prod/us-east-1
terragrunt run --all apply --terragrunt-working-dir prod/us-east-1

# Deploy single component
terragrunt apply --terragrunt-working-dir prod/us-east-1/services/frontend-app
```

Cloud Posse's Atmos builds on Terragrunt patterns with additional conventions.
