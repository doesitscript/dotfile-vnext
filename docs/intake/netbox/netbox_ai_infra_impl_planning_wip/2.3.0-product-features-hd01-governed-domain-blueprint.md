```markdown
# HD-01 — Harmonic Work Domain
## Private Local AI Product Engineering Lab

### Purpose
Create a governed work domain for developing private/local AI-enabled products, dashboards, agents, and evaluation workflows using the user's home lab infrastructure.

### Primary posture
This domain is for building product capabilities, not merely hosting models.

### Work hosted here
- Local LLM serving
- AI dashboard development
- Prompt and workflow experimentation
- Evaluation harnesses
- Langfuse observability
- RAG / memory systems
- Agent/tool integration
- Private data handling
- Local-first product prototypes

### Not primary scope yet
- Training foundation models from scratch
- Large-scale distributed ML training
- Enterprise multi-agent orchestration
- Public SaaS deployment

### Relationship to existing lab
This domain extends the existing Ansible-managed homelab, vLLM node, network/server node, GPU hosts, NetBox inventory discipline, and now/later LiteLLM gateway strategy.

### Deployment posture
- Mac dev machine remains the controller / operator / IDE surface
- RTX 5090 server becomes the primary local reasoning/model-serving lane
- Medium GPU desktop/server becomes experiment, reviewer, embedding, and secondary model lane
- Network/storage server hosts shared observability, artifact storage, databases, and durable services
```

```markdown
# HWC-01 — Harmonic Execution Cell
## AI Product Development Execution Cell

### Purpose
A focused execution cell for turning vetted conversation ideas into runnable local AI product features.

### Core development work types
1. Model serving
   - vLLM
   - Ollama as lightweight fallback/playground
   - LiteLLM gateway

2. Application development
   - dashboard frontend
   - API/backend service
   - user/session/project state
   - auth later, not first

3. Evaluation and observability
   - Langfuse
   - prompt traces
   - scoring
   - regression tests
   - “lie detector” style confidence/contradiction/claim-check dashboarding

4. Data and memory
   - Postgres
   - Redis
   - ClickHouse if Langfuse requires it
   - object storage via MinIO
   - embeddings/vector search later

5. Agent/tooling layer
   - MCP tools
   - repo tools
   - shell/Ansible helpers
   - Notion/NetBox governance intake

### First viable product direction
Build a local AI workbench/dashboard that can:
- send prompts through LiteLLM
- route to local vLLM/Ollama models
- trace runs in Langfuse
- compare model responses
- score usefulness, confidence, contradiction, hallucination risk
- attach conversation/product notes into governed structures

### Do not overbuild first
Avoid starting with:
- Kubernetes-first everything
- full multi-agent orchestration
- custom model training
- complicated RAG before evaluation exists
- too many models at once
```

What you should build first:

```markdown
# First Implementation Slice

## Goal
Create a working local AI product-development loop.

## Deploy first
- LiteLLM gateway
- one vLLM-served model on RTX 5090 host
- Ollama fallback/playground
- Langfuse on network/storage server
- Postgres/Redis/ClickHouse/MinIO as needed
- simple dashboard/API app
- Ansible inventory + service definitions
- NetBox entries for hosts, services, ports, and ownership

## Prove
- Mac/Cursor can call LiteLLM
- LiteLLM can route to vLLM
- responses are traced in Langfuse
- dashboard can display prompt, response, model, latency, cost/token estimate, score, and notes
- one repeatable evaluation can compare two model outputs

## Then add
- embeddings
- local document ingestion
- RAG
- MCP tools
- agent recipes
- stronger dashboard scoring
```
