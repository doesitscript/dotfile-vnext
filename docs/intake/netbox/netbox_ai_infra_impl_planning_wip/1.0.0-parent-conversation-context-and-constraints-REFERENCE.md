## Exchange 1 — Multi-agent foundations vs orchestration

### User

> Do not start with multi-agent complexity — agreed — but we're still going to have the building blocks for multi-agent work. Just mentioning so you understand I recognize this but am not pushing for multi-agent implementation until it makes sense.
>
> *"Your edge/dev host NetBox plan already anticipates modeling additional GPU/dev hosts and services like Ollama/LiteLLM later"* — **later is now**. I'll be using or making available the second medium-power GPU for what you identified above. Why? By thinking in terms of multiple GPUs (even just two), I lay groundwork for designing projects and the above for scalability and maturity (I avoid snowflake work).
>
> So yes, I'm not targeting multi-agent architecture, but I will need to implement several agent types and models. **Confirm or add any restrict before I proceed with my next request.**

### Assistant — Confirmed

**Your constraint should be:**

Build multi-agent-capable **foundations** now, but do **not** prematurely build a full multi-agent orchestration platform.

**Second GPU “later is now” is correct** because it affects the shape of the foundation:

- Model lanes need to be designed for more than one backend
- NetBox should model the second GPU host/services **now**
- LiteLLM should route by alias/purpose, not hardcoded host
- Langfuse traces should record: agent role + model lane + GPU/backend
- RIPI should track work items and agent runs even if there is only one real agent at first
- Privacy policy must apply **before** routing to either GPU or Azure

**The restriction I’d add:**

Do **not** make the second GPU an equal peer by default. **Give each GPU a job.**

**Recommended:**

| Lane | Role |
|------|------|
| **5090 lane** | Primary deep local reasoning, heavy coding, vLLM primary, sensitive/private work |
| **Second GPU lane** | Parallel reviewer/tester agents, smaller models, embeddings, experiments, fallback local lane |

So yes: implement several agent types and model lanes **now**.

But keep the **first executable workflow** simple:

```text
capture work → classify privacy → choose model lane → run one bounded agent role
  → trace result → test/verify → promote/reject
```

That gives you scalability without snowflake chaos.
