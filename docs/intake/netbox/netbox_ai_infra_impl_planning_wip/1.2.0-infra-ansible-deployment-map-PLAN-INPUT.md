### Assistant — Implementation plan

Implementation map you can adapt directly into Ansible: node placement, roles to create, variables to define, service exposure, and what Mac/IDE should consume.

**Core decision:**

| Resource | Role |
|----------|------|
| **5090** | Primary private/deep model lane |
| **Second GPU** | Reviewer/tester/embedding/parallel lane |
| **Third medium GPU** | Experimental/fallback/dev-agent lane |
| **Mac** | Operator + IDE + orchestration surface |
| **K3s** | Shared platform services |
| **Docker VMs** | Heavier stateful/support services where they already fit |

Your existing estate already supports this split: **mac-dev** is execution/operator; GPU lane has **dkr-02** and **k3s-02**; Langfuse/LiteLLM/Jupyter on **k3s-02**; NetBox/Semaphore/Loki/Grafana/Postgres/MinIO around **dkr-02**.

### 4. vLLM placement

You do **not** necessarily need vLLM on every server. You need vLLM where you want OpenAI-compatible high-throughput model serving.

| Host | vLLM? | Why |
|------|-------|-----|
| 5090 node | **yes** | Primary deep/private inference |
| Second GPU node | **yes**, smaller profile | Reviewer/tester/parallel local inference |
| Third GPU desktop | optional | Experiment/fallback |
| Mac | **no** | Client only |
| k3s-02 | maybe | Only if GPU attached or orchestrated runtime |
| dkr-02 | **no** | Support/stateful services, not inference |

Existing vLLM plan treats this as runtime/cache foundation, not the long-term model catalog. **Keep that boundary.**

**Role:** `roles/ai_vllm_runtime`

**Variables (placeholder hosts/models):**

```yaml
ai_vllm_instances:
  - name: vllm-primary-5090
    host: hom-lab-ctl-hvh-02-or-gpu-vm
    lane: private-deep
    gpu_profile: primary
    model_profile: coding-deep
    port: 8001
    publish: true

    host: second-gpu-host
    lane: reviewer-tester
    gpu_profile: secondary
    model_profile: coding-review
```

### 5. Ollama placement

Use Ollama as a simpler local dev/runtime tool, not your serious gateway.

| Host | Ollama? |
|------|---------|
| 5090 | optional |
| Second GPU | **yes** |
| Third GPU | **yes** |
| Mac | optional client/dev only |

Ollama: quick model tests, embeddings, lightweight local agent work. **vLLM** is the deliberate serving runtime.

### 6. LiteLLM placement

**One central gateway on k3s-02.** Do not run random LiteLLM gateways everywhere unless you need edge failover.

LiteLLM = multi-model control plane for agents and IDE workflows, **not** the runtime itself.

**LiteLLM model aliases (placeholders):**

```yaml
model_aliases:
  ripi-private:
    backend: vllm-primary-5090
    privacy: local_only

  code-deep:
    backend: vllm-primary-5090
    privacy: local_first

  code-review:
    backend: vllm-secondary-reviewer
    privacy: local_first

  code-test:
    backend: vllm-secondary-reviewer
    privacy: local_first

  embeddings-local:
    backend: second-gpu-or-ollama
    privacy: local_only

  experiment:
    backend: third-gpu-desktop
    privacy: local_only

  azure-reasoning:
    backend: azure
    privacy: public_or_sanitized_only
```

**OpenClaw** should call LiteLLM, not individual model endpoints directly when possible. Treat it as an agent surface that must obey privacy/routing layer.

**Restriction:** OpenClaw-style agents can act across tools/channels — do not give broad permissions until local routing, audit, and approval gates are in place (ecosystem has drawn security/privacy scrutiny around broad permissions and prompt-injection risk).

### 10. RIPI dashboard V0 resources

Deploy RIPI as a **small app**, not a giant platform.

| Component | Placement |
|-----------|-----------|
| RIPI web UI | k3s-02 |
| RIPI API | k3s-02 |
| RIPI DB | dkr-02 Postgres or dedicated Postgres |
| Trace links | Langfuse |
| Model routing | LiteLLM |
| Model/cache metadata | Postgres first; NetBox later for infra/service objects only |

**RIPI should track:**

- WorkItem
- AgentRun
- ModelLane
- ContextClass
- PromotionReceipt
- Endpoint
- TraceLink
- RepoBinding

### 11. Implementation order

1. NetBox/dev fleet modeling for second/third GPU nodes
2. Hugging Face client/cache role
3. NVIDIA runtime verification role for each GPU host
4. vLLM primary on 5090
5. vLLM secondary on second GPU
6. LiteLLM aliases pointing at both

8. Mac IDE/client config pointing to LiteLLM
9. OpenClaw gateway pointed to LiteLLM
