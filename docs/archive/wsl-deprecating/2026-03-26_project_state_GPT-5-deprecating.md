## What This Repo Actually Is

At its core, `dotfile-vnext` is an Ansible-managed infrastructure repo for a heterogeneous AI/dev environment spanning:

- macOS controller (`mac-dev`)
- Windows hosts managed through WinRM (`*-win`)
- Linux companion surfaces reached by SSH (`*-wsl`, legacy naming)
- an emerging direct Linux VM path (`linux_vm_hosts`, currently `server-225-ubuntu`)

The repo is not just "dotfiles." It is trying to standardize:

- host bootstrap
- access surfaces
- development tooling
- Docker and stack deployment
- logging
- MCP tooling for AI-assisted workflows
- AI agent operating behavior itself

## Architecture Snapshot

### Inventory model

`inventory/inventory.yaml` is one of the clearest design surfaces in the repo. It encodes several durable truths:

- `*-win` is the Windows bootstrap/control surface
- `*-wsl` is legacy naming for Linux companion hosts that may be SSH-ready
- `linux_vm_hosts` is the newer non-WSL Linux companion path
- physical-node groups such as `server_225` group all surfaces of one machine
- runtime grouping via `group_by` is used for intent-driven targeting such as `node_purpose_development`

This is a good sign. The inventory is not random accumulation; it reflects an intentional host model.

### Playbook strategy

The repo has 31 playbook files under `playbooks/` and `playbooks/mac/`. The most credible current control surfaces are the focused ones, for example:

- `playbooks/mac/ansible_dev_tools.yaml`
- `playbooks/mac/mcp_servers.yaml`
- `playbooks/deploy_development_nodes.yaml`
- `playbooks/provision_server_225.yaml`
- `playbooks/server_225_multipass_ubuntu_vm.yaml`
- `playbooks/troubleshoot/collect_multipass_windows_artifacts.yaml`

The direction is toward smaller, clearer playbooks rather than one giant bootstrap entrypoint.

### Role strategy

There are 37 top-level role directories. The repo is decomposed by capability area, not just by host. That is a healthy sign. Examples:

- base/dev tooling: `ansible_dev_tools`, `direnv`, `cursor`, `git`, `python`, `tmux`, `pwsh`
- infra/runtime: `docker_engine`, `docker_client`, `logging_loki`, `logging_alloy`, `k3s_*`
- host families: `server_225/*`, `network_server/*`, `dev_3090/*`
- access/control: `access_identity_controller`, `access_identity_windows`, `transport_execnode_ssh`
- AI/MCP: `mcp_inspector`, `roles/mcp_servers/*`
- current troubleshooting/transition work: `multipass_ubuntu_vm`, `troubleshooting_collectors`

### AI framework maturity

This repo is unusually mature in one dimension: it has an explicit AI operating model.

Evidence:

- `AGENTS.md` gives durable repo behavior
- `docs/codex_framework/*` defines planner/researcher/executor expectations

## Highest-Signal Risks And Drift

### 1. Front-door docs are stale in important places

The root `README.md` still references paths that are currently absent, including:

- `playbooks/bootstrap_execution_node.yaml`
- `playbooks/boostrap_windows_ssh_via_winrm.yaml`
- `playbooks/bootstrap_server_225.yaml`
- `playbooks/bootstrap_local.yml`
- `playbooks/deploy_shell_config.yaml`
- `docs/architecture_rules.md`

This matters because a new AI might start at `README.md` and immediately build on non-existent entrypoints.

### 2. Wrapper-era docs and native-Ansible docs coexist

`docs/ansible/native-ansible-first.md` de-emphasizes `./bin/fz`, but `docs/operator_runbook.md` still centers it heavily. Another AI should treat wrapper-driven flow as background or legacy unless current files prove otherwise.

### 3. Secret handling is inconsistent

The repo clearly knows how to use vaults. There are vault templates, encrypted group vars, and README guidance. But current Windows host vars still contain plaintext credentials such as:

- `inventory/host_vars/hom-lab-ctl-hvh-02.yaml`
- `inventory/host_vars/home-lab-auth-hvh-01.yaml`
- `inventory/host_vars/dev-workstation-win.yaml`

Even if these are placeholders, their presence is a maturity/security smell because they normalize plaintext host secrets in the main inventory layer.

### 4. Transitional state is real, not cosmetic

The repo is actively translating from older WSL-oriented assumptions toward a Multipass/Linux-VM model. Evidence:

- `inventory/inventory.yaml` explicitly labels `-wsl` as legacy naming
- `inventory/group_vars/linux_vm_hosts.yaml` introduces a new direct Linux VM group
- `inventory/host_vars/hom-lab-ctl-hvh-02.yaml` carries `multipass_ubuntu_vm_*` variables
- `playbooks/provision_server_225.yaml` retains `server_225/wsl2` as legacy reference while adding `multipass_ubuntu_vm`

That means another AI should not overgeneralize from the old WSL path.

### 5. Verification exists, but enforcement is not fully active

The repo has:

- `.ansible-lint`
- `docs/ansible/quality-gate.md`
- `.pre-commit-config.yaml`

But `.git/hooks/pre-commit` is not installed in this working copy. So verification is configured, not guaranteed.

### 6. Runtime framework enforcement is not fully validated

The repo has substantial Codex-framework material, and this session itself is
evidence that at least part of the framework is working. But I did not find
direct evidence that:

- `.cursor/rules/*.mdc` are the exact rule surfaces injected into Codex
  sessions
- separate-agent Codex execution is already happening in normal workflow

This should be tracked as an explicit follow-up rather than guessed.
