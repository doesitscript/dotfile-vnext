# Ansible Project Review (Current State)

This document captures the detailed review of the Ansible project conducted on **February 24, 2026**.  It summarises the layout, inventory, playbooks, roles, dependencies, documentation, and recommendations.

---

## 🔍 1. Project layout at a glance

```
/
|– ansible.cfg                  # central configuration
|– inventory/                   # YAML inventory, host_vars, group_vars
|– playbooks/                   # small orchestration playbooks
|– roles/                       # ~20 roles, each with README/structure
|– vault/                       # encrypted vars, password script
|– requirements.yml             # galaxy collections & roles
|– bin/ … scripts/ … docs/ …    # helpers, notes, bootstrap helpers
|– .cursor/                     # indexing rules & documentation hints
```

Everything related to Ansible lives in the top‑level tree; there’s no hidden “meta‑repo” or external dependency.  `ansible.cfg` has a full, well‑commented configuration block that documents the choices (fact‑caching, control path, WinRM tuning, etc.).

---

## 🧭 2. Inventory & variable hierarchy

- **Dual‑surface model.**  Each Windows physical node appears twice (`…‑win` for WinRM bootstrap, `…‑wsl` for the Linux companion side once it is directly reachable over SSH).  
‑‑> children `windows_hosts` and `wsl_hosts` are grouped under `ssh_targets` when SSH entries are needed.

- **Group‑vars** exist for every purpose (`all`, `execution_nodes`, `windows_hosts`, the physical‑node groups such as `server_225`, etc.).  File names match the inventory groups (Appreciate the comment in `inventory.yaml` explaining the naming pattern).

- **Host‑vars** are generated by bootstrap scripts on the hosts; the example `hom-lab-ctl-hvh-02.yaml` contains all connection parameters (including `ansible_port`, `ansible_user`, `winrm_transport`, etc.) and even the “docker engine” SSH proxy configuration.

- **Variable merging & precedence** follow the documented Ansible rules.  The repository’s `group_vars` files use jinja logic to set OS‑specific defaults (see `all.yaml` for the `dotfiles_home` and `dotfiles_user_home` expressions).

> ✅ Cursor is already aware of `ansible-inventory-guide`, `ansible-var-merge`, `ansible-variable-precedence` etc., so any advice involving this structure will be grounded in the official behaviour.

## 📄 3. Playbooks

Playbooks are extremely lean:

- `playbooks/access.yaml` simply imports two others (`access_controller.yaml` and `access_windows.yaml`) and then runs a small local task to regenerate the SSH client config.

- There are dedicated plays for bootstrapping (`bootstrap_server_225.yaml`, `bootstrap_network_server.yaml`, etc.), for Docker (`docker.yaml`, `docker_engine.yaml`, `docker_client.yaml`, `verify_docker.yaml`) and for “access”/identity work.

- The imported‑playbook pattern avoids duplication and makes limiting (`--limit`) easy.

- Comments at the top of each file explain its purpose and show example invocations.

## ⚙️ 4. Roles

The `roles/` directory is richly populated.  A few high‑level notes:

- Role names fall into the categories defined in `.cursor/rules/role_conventions.md` (access/identity, common, node‑specific, tooling).  
- Each role has a `tasks/main.yml` and, when multi‑OS, includes an `include_tasks: "{{ ansible_os_family | lower }}.yml"` pattern.  
- Default variables are kept in `roles/<name>/defaults/main.yml` (I inspected several; they are concise and documented).  
- Many roles ship platform‑specific files: e.g. `mac.yml`, `ubuntu.yml`, `windows.yml`.  Windows tasks consistently use `ansible.windows.*` or `community.windows.*` FQCN modules.  
- Task naming is outcome‑oriented; handlers are used for service restarts.  
- Some roles (e.g. `access_identity_windows`) use tags to separate admin vs. user actions.

Examples of roles you can glance at:

- `access_identity_controller/tasks/main.yml` – generates SSH keys, publishes cached facts, optionally manages known_hosts.
- `mac_dev/…`, `server_225/…`, `network_server/…` – hardware‑specific configuration, usually included from the bootstrap playbooks.
- Tooling roles like `python/`, `git/`, `tmux/`, `vscode/` install packages with Homebrew on macOS or use appropriate OS package managers.

## 📦 5. Dependencies

`requirements.yml` pins a small set of collections:

```yaml
collections:
  - ansible.posix
  - ansible.windows
  - community.crypto
  - community.docker
  - community.general
  - community.windows
  - https://github.com/myllynen/windows-ansible-roles   # git source

roles:
  - geerlingguy.docker @ 7.4.1
```

You call `ansible-galaxy collection install -r …` and `ansible-galaxy role install -r …`.  The pinned versions and explicit git URL are good practice.

## 🔐 6. Secrets & vaults

- A vault password script (`vault_pass.sh`) is referenced in `ansible.cfg`.
- Encrypted files live under `vault/` (`shared.vault.yml`, `main.vault.yml`, plus individual vaults such as `openssh_host_keys.vault.yml`).
- `shared.vault.yml` contains placeholders and examples; `vault_server_225_win_password` is present there as well as in plaintext in a host_vars file – you may want to move the latter entirely into vault.
- Ensure `.vault_pass` is created per `config/README_vault_pass.md`.

## ✅ 8. Best‑practice adherence

The repository exhibits a number of strong patterns:

1. **Descriptive task names** and modular roles.  
2. **Host‑level fact caching** used to propagate `ssh_configured` hints across plays.  
3. **Clear separation of concerns** – bootstrap vs. ongoing configuration.  
4. **Use of standard collections** rather than hand‑rolled modules.  
5. **Config comments** explain why things (like `host_key_checking = false`) are done.  
6. **Inventory naming conventions** make it easy to write group‑specific vars.  
7. **Cursor doc integration** ensures AI assistance will respect current Ansible behaviour.

---

## ⚠️ 9. Opportunities for improvement

1. **Encrypt plaintext passwords** in `inventory/host_vars`; the file `hom-lab-ctl-hvh-02.yaml` contains `Pass@w0rd1`.  Either remove them or vault‑encrypt the host_vars file.  
2. **Add linting / CI**:  
   - A simple `.ansible-lint` or `tox.ini` / GitHub Action could catch syntax/style issues before they’re committed.  
   - `yamllint` might help with the long YAML files.  
3. **Unit testing** (molecule or simple dry‑run checks) could validate roles/plays against a container image.  
4. **Consider moving some magic values** (timezones, port numbers) into group_vars defaults if they are replicated.  
5. **Document known‑good Ansible version** and perhaps pin the controller to it in a `requirements.txt`/virtualenv.

These are mostly “nice‑to‑haves”; the current code is already very solid.
