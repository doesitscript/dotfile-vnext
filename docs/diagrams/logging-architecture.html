Design Strengths
  • Single playbook, two plays — clean separation of server vs. agents
  • Platform dispatch via os_family — no host-specific conditionals in playbook
  • Tag granularity: install/config split enables config-only runs
  • WinRM guard (pre_task end_host) prevents SSH-mode Windows confusion
  • Loki ready-check: blocks until healthy before returning
  • Docker pre-flight verify at play start (always tag)
  • Three handler names (Windows/Linux/macOS) — correct platform isolation
  • logging_server group defined in inventory — not embedded in playbook
  • Both roles have defaults/, handlers/, templates/ — proper role structure

How Loki Works — Push Model (NOT a Shared Drive)
IMPORTANT: Loki is a log aggregation server, not a shared file store
Each Alloy agent collects logs locally on its own machine (Event Log, journald, files) and pushes them over HTTP to Loki's API endpoint (POST /loki/api/v1/push). Loki stores the compressed log chunks on its own local disk (or object store like MinIO).

There is no shared folder, no NFS mount, no SMB drive that agents write to. The E Drive is where Loki itself stores its database — agents never touch it directly. This is the same model as Prometheus: agents forward metrics/logs to a central server over HTTP.
