- `playbooks/deploy_k3s_data_disk.yaml` encodes attachment before guest mount.
- `roles/hyperv_vm_data_disk/` manages one exact secondary VHDX with
  `present|absent`; Apply defaults false, present requires selected values plus
  backup/authority, and absent detaches without deleting the file.
- `roles/linux_data_disk_mount/` manages one exact non-OS disk with
  `present|absent`; it resolves a stable by-id path, rejects `/dev/sda`, requires

## S5 owner decision package

Current repo/live evidence has journald on the K3s guest, Alloy forwarding
journal data to Loki, and Loki/Grafana on the logging lane. It has no proven
Prometheus, Alertmanager, node_exporter or PrometheusRule owner. Loki retention
is log retention and is not node-storage metrics/alerting.

Recommended smallest current-stack option: a host-native systemd disk check and
timer whose structured failures enter journald and existing Alloy/Loki. Choose
this only if dashboard/log visibility without paging meets the requirement.
If alert routing/paging is required, select the larger Prometheus-compatible
metrics plus Alertmanager capability instead.

Required user choices: owner option; cadence; warning and critical percentages;
mounts in scope; alert destination/route; log/metric retention. No executable
policy is authored until those values are selected.

## Apply / Verify / Undo / Change class

- Apply: repository-only lifecycle scaffolding; no VHDX, partition, filesystem,
  mount, cache/PVC, workload or monitoring mutation.
- Verify: exact commands above, including both fail-closed negative branches.
- Undo: revert the two roles/playbook and campaign updates. Future runtime undo
  must unmount before detach and preserve the VHDX/backup.
- Change class: idempotent capability scaffolding with destructive operations
  disabled behind explicit identity, backup and authority gates.
