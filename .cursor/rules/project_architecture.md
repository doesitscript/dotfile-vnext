# Project Architecture — dotfile-vnext

This rule provides essential context about the project structure. Read this before doing anything.

## What This Project Is

An Ansible-managed hybrid infrastructure project controlling Windows, WSL, and macOS machines on a home lab LAN. Everything runs from a Mac controller (`mac-dev`) using Ansible over WinRM (Windows) and SSH (WSL/Linux).

## Dual-Surface Model (Critical Concept)

Each Windows physical node exposes **two inventory surfaces**:

- `<node>-win` — Windows surface, managed via **WinRM** (port 5985, NTLM)
- `<node>-wsl` — WSL surface, managed via **SSH** (port 22, key-based)

Example: The physical machine `server-225` appears as both `server-225-win` and `server-225-wsl` in inventory.

## Connection Resilience

When executing remote commands, multiple connection paths exist. If one fails, try another before giving up:

| Target      | Primary                   | Fallback(s)                                                                  |
|-------------|---------------------------|------------------------------------------------------------------------------|
| Windows     | WinRM                     | SSH to `-win-powershell` (port 2223); SSH to WSL then `wsl.exe` into Windows |
| WSL         | SSH to `-wsl`             | SSH to `-win` (lands in WSL via DefaultShell); WinRM then `wsl -d <distro>` |
| Mac (local) | Local / connection: local | N/A                                                                         |

## Inventory Groups

- `execution_nodes` — Mac controller (local connection)
- `windows_hosts` — All `-win` surfaces (WinRM)
- `wsl_hosts` — All `-wsl` surfaces (SSH)
- Physical node groups (`server_225`, `network_server`, `dev_3090`) — contain both surfaces

## Directory Layout

```
params/site.yaml          — Source of truth for IPs, users, drive letters
inventory/
  inventory.yaml          — Main inventory (groups + hosts)
  hosts_mapping.yaml      — Physical node hostname/IP detection
  group_vars/             — Per-group variables
  host_vars/              — Per-host variables (partially generated by bootstrap)
playbooks/                — Top-level playbooks (import roles)
roles/
  access_identity_*/      — SSH/OpenSSH identity and access
  transport_execnode_ssh/  — Execution node SSH setup
  common/baseline/        — Timezone, node facts (multi-OS)
  common/shell_config/    — .bashrc.d pattern, aliases
  ansible_dev_tools/      — Ansible tooling installation
  <node_name>/            — Node-specific roles (e.g., server_225/, dev_3090/)
bin/                      — Bootstrap scripts (PowerShell + bash)
```

## Variable Flow

`params/site.yaml` → bootstrap scripts → `host_vars/` and `group_vars/` → playbooks → roles

Bootstrap scripts read `params/site.yaml` and generate `host_vars/*.yaml` files. Playbooks and roles consume those generated vars. Do not hand-edit generated host_vars without understanding this flow.

## Bootstrap Chain

1. `bin/bootstrap-local.ps1` — Run on Windows as Admin. Detects node, configures WinRM, generates host_vars.
2. `bin/bootstrap-ansible-local.ps1` — Provisions WSL distro via cloud-init, runs bash bootstrap inside WSL.
3. `bin/bootstrap-local.sh` — Inside WSL: sets up SSH server, passwordless sudo.
4. Ansible playbooks take over from the Mac controller after bootstrap completes.
